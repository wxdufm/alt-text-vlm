# Album-Cover Alt-Text Generation

A repository of WCAG 2.2-compliant alt text for album-cover artwork, generated by fine-tuning a
local vision-language model on a human-verified training set sourced from WXDU's release
database. See `context.md` for the full project scope and `full_fine_tuning_report.md` for a
detailed account of the fine-tuning process (seven trials, two output formats, and everything
learned along the way).

## Architecture

This repo is really two things stitched together: WXDU's internal alt-text generation/review
pipeline (needs access to WXDU's live systems), and the fine-tuning pipeline that turns reviewed
data into a model (works standalone off the [public dataset](#dataset)). If you're picking this up
from outside WXDU, you mostly care about the second half.

**The three servers** (easy to mix up, since two of them serve very similar-sounding "generate alt
text" purposes):
- `server.js` — the internal human-review tool. Talks to the live Postgres DB, serves
  `public/review_website`. Reviewers claim a release, see the model's draft alt text, and
  confirm/correct it.
- `alt_text_server.js` — a separate generation *playground*, for trying different trained adapters
  against known releases and comparing output. Serves `public/alt_text_generation_website`, and
  spawns...
- `scripts/inference_server.py` — ...the actual Python/`mlx_vlm` inference backend.
  `alt_text_server.js` talks to it over HTTP, since Node can't call `mlx_vlm` directly.

**How a release becomes a training row** (the data pipeline, roughly in order):
1. `scripts/generate-testdata.js` pulls releases from WXDU's live API (falling back to a Discogs
   search for cover art when needed), runs a base VLM on each cover via Ollama, and inserts drafts
   into Postgres (`releases`/`release_ids`).
2. A human reviews each draft through `server.js`/`public/review_website`, which sets
   `approved = true` and logs before/after in `reviews_history`.
3. `scripts/export_data.js` pulls the approved, human-reviewed releases out of Postgres into
   `data/train.jsonl`/`valid.jsonl`/`train_test.jsonl`, downloading cover images to `data/covers/`
   along the way.
4. `scripts/train_lora_with_val.py` fine-tunes a LoRA adapter against those JSONL files, producing
   checkpoints under `adapters/<trial>/`.
5. `scripts/04_generate_alt_text.py` (batch) or `scripts/test_single.py` (one row) evaluate a
   trained adapter against `data/valid.jsonl` — see [Generating alt text](#generating-alt-text-with-a-trained-adapter).

**Folders at a glance:**

| Path | What it is |
| --- | --- |
| `migrations/` | the [public dataset](#dataset) — schema + CSV seed data, self-contained |
| `data/` | JSONL training/validation splits, plus local cover images in `data/covers/` (gitignored — see [Dataset](#dataset)) |
| `adapters/` | trained LoRA checkpoints, one folder per trial (e.g. `adapters/3rd-trial/700`) |
| `scripts/` | the data pipeline: generation, export, training, evaluation |
| `lib/` | shared connection helpers (`postgres.js` is used; `mongodb.js` is currently unused dead code) |
| `prompts/` | prompt templates filled with artist/title and sent to the VLM |
| `public/` | the two web frontends — `review_website` (for `server.js`) and `alt_text_generation_website` (for `alt_text_server.js`) |
| `eval_results/` | per-trial output from `scripts/04_generate_alt_text.py` |
| `training_logs/` | raw training logs, one file per trial |
| `pilot/` | an early exploratory model comparison (30b vs. 8b outputs, side by side), predates the main pipeline |
| `Modelfile-8b` / `-30b` / `-32b` | Ollama configs for the base VLMs used in initial dataset generation (`context.md`'s Stage 1) |
| `context.md` | the original project scope/methodology write-up |
| `full_fine_tuning_report.md` | the complete, detailed account of all 7 fine-tuning trials |
| `discogs_review_tmp/` | scaffolding used to backfill Discogs/MusicBrainz ids into the public dataset — gitignored, kept around for reference, not part of the core pipeline |

## Prerequisites

- **Node.js and npm** — for the review tooling and data-export scripts (`server.js`,
  `scripts/*.js`).
- **PostgreSQL** — for the dataset and review database (developed against Postgres 18).
- **Python 3.11+ on Apple Silicon, with [mlx-vlm](https://github.com/Blaizzy/mlx-vlm)** — for
  fine-tuning and generation. `mlx` (the ML framework mlx-vlm is built on) only runs on Apple
  Silicon Macs, so this project's fine-tuning/generation pipeline assumes that hardware. **If
  you're not on Apple Silicon, mlx-vlm isn't an option for you** — you'll need to find and adapt
  your own fine-tuning stack (e.g. Hugging Face `transformers` + `peft`/`accelerate` on CUDA), and
  `scripts/train_lora_with_val.py`/`scripts/test_single.py` will need rewriting against whatever
  you pick.
- A **Discogs API token** — only needed for the id-matching scripts under `discogs_review_tmp/`,
  not for fine-tuning or generation.

## Setup

1. Clone the repo.
2. `npm install`
3. Set up the Python side (a virtualenv or conda env is recommended), matching the Python 3.11+ /
   Apple Silicon note above:
   ```
   pip install -r requirements.txt
   ```
4. `cp .env.example .env` and fill in real values — at minimum `PG_URI`, pointing at your own
   Postgres instance.
5. Load the dataset:
   ```
   createdb your_db_name
   psql "$PG_URI" -f migrations/001_public_schema.sql
   ```
   (see [Dataset](#dataset) below for what this actually creates).

## Dataset

The public, shareable dataset lives in `migrations/001_public_schema.sql` and
`migrations/seeds/*.csv`. Running the migration against an empty Postgres database recreates it
in full (the `\copy` paths inside are relative to wherever you run `psql` from, so run it from the
repo root, as in [Setup](#setup) above).

It's restricted to releases that are human-approved with a final alt text under 131 characters —
**524 releases** in total, across five tables:

| Table | What it holds |
| --- | --- |
| `releases` | artist, title, alt text, confidence score/explanation, review triggers, and a perceptual hash of the cover (`cover_hash`) |
| `release_ids` | the Discogs and/or MusicBrainz id for each release, where one could be found and visually confirmed against the actual cover art |
| `reviews_history` | the model's original output vs. the final human-approved version for each release, and whether it was confirmed or denied |
| `review_trigger_definitions` | the fixed vocabulary of reasons a release might need human review (e.g. "bad image quality") |
| `release_claims` | ships empty — an internal reviewer-locking mechanism, not meaningful outside the live review tool |

Of the 524 releases, **479 (91%) have at least one of a Discogs/MusicBrainz id** — 378 have both,
79 Discogs-only, 22 MusicBrainz-only. The remaining 45 are niche/self-released titles that don't
appear to be cataloged on either service. A match was only ever accepted after visually confirming
the candidate's cover art actually matches ours (via perceptual-hash comparison), never from an
artist/title text match alone.

The dataset itself doesn't include cover images or URLs — album art is copyrighted, and both id
types are enough to look artwork up yourself via the Discogs or MusicBrainz APIs. The local
training data (`data/train.jsonl`, `data/valid.jsonl`) is separate from this public dataset and
references cover images downloaded locally to `data/covers/<release id>.<ext>` (gitignored, not
tracked in this repo) — you'll need to fetch those yourself before fine-tuning will actually run,
e.g. via the Discogs/MusicBrainz ids in `migrations/seeds/release_ids.csv`.

## Fine-tuning your own model

Fine-tuning uses mlx-vlm's LoRA trainer via `scripts/train_lora_with_val.py` — a thin wrapper
around `mlx_vlm.lora` that actually wires up validation-loss tracking (the stock `mlx_vlm.lora`
CLI accepts a `--val-dataset` flag but silently ignores it).

```
python scripts/train_lora_with_val.py \
    --model-path mlx-community/Qwen3-VL-8B-Instruct-4bit \
    --train-dataset data/train.jsonl \
    --val-dataset data/valid.jsonl \
    --output-path adapters/my-trial \
    --batch-size 4 \
    --lora-rank 16 \
    --train-on-completions \
    --epochs 8
```

A few things worth knowing before you start:
- Checkpoints land in `--output-path` periodically (per `--steps-per-save`, default every 50
  steps) — see `adapters/*/` for examples from the 7 trials already run here (the numbered
  subfolders are training iterations, e.g. `adapters/3rd-trial/700`).
- `--lora-rank`/`--lora-alpha`, batch size, and output tag format (whether the prompt asks for a
  `confidence-reasoning` tag) were the main things varied across trials — see
  `full_fine_tuning_report.md` for what worked and what didn't before picking your own.
- This whole pipeline (`mlx_vlm.lora`'s trainer underneath) is Apple-Silicon-only — see
  [Prerequisites](#prerequisites).

## Generating alt text with a trained adapter

The most direct way to run any adapter against any image — a local file or an http(s) URL — is
mlx-vlm's own generate CLI:

```
python -m mlx_vlm.generate \
    --model mlx-community/Qwen3-VL-8B-Instruct-4bit \
    --adapter-path adapters/3rd-trial/700 \
    --image /path/to/cover.jpg \
    --prompt "Generate accessibility alt text for this album cover.
Artist: Some Artist
Album title: Some Album"
```

`--image` also accepts a URL directly — confirmed working against a plain image host, but **not**
against Discogs' own image CDN (`i.discogs.com`) or Wikimedia, both of which returned `403
Forbidden` when tested: `mlx_vlm`'s fetch doesn't send the headers those CDNs require to allow
non-browser requests. If a URL 403s, download the image locally first and pass the file path
instead. Swap `--adapter-path` for any checkpoint under `adapters/` — e.g. `adapters/7th-trial/800`
or `adapters/5th-trial/900` (see [Results](#results) below for how each trial performed) — and
fill the `{{artist}}`/`{{title}}` placeholders in `prompts/short_prompt.txt` with the real release
info for a properly-formatted prompt.

Two other ways to do the same thing, already built into this repo:
- `python scripts/test_single.py --index 0 --adapter-path adapters/3rd-trial/700` — runs one row
  from `data/valid.jsonl` (by index or release id, via `--id`) and prints the model's prediction
  next to the human-written reference, useful for quick spot-checks against known-good examples.
- The interactive web UI: `node alt_text_server.js`, then open `public/alt_text_generation_website`
  in a browser. Lets you pick a trial from a dropdown and a cover by release id (random, by
  dataset index, or typed in) — but only works for releases already in your database with a local
  cover or `cover_url`, not arbitrary external images.

## Results
We did a total of 7 trials to fine-tune a working model. After each trial, we analyzed the model output to try to understand why it wasn’t performing as expected, and then changed parameters or improved data quality as needed to make the next trial better. Each trial’s adapters with the lowest val loss were tested on a validation dataset of 80.

Here are the results

| Trial | Base precision | LoRA Rank / α | Output format                            | Best checkpoint   | Val loss (min)       | Well-formed       | Within 130 char | Avg. similarity |
| ----- | -------------- | ------------- | ---------------------------------------- | ----------------- | -------------------- | ----------------- | --------------- | --------------- |
| 1st   | 4-bit          | 8 / 16        | long in-context style guide (broken)     | final (only save) | not tracked          | **0/80 (0%)**     | 0/80 (0%)       | 0.000           |
| 2nd   | **8-bit**      | 32 / 16       | 4-tag                                    | checkpoint 700    | 0.779 @700           | **78/80 (97.5%)** | 69/80 (86.3%)   | 0.496           |
| 3rd   | 4-bit          | 32 / 16       | 4-tag                                    | checkpoint 700    | 0.789 @700–800       | **79/80 (98.8%)** | 73/80 (91.3%)   | 0.488           |
| 4th   | 4-bit          | 16 / 8        | 4-tag (standardized reasoning, 133 rows) | final (iter 3552) | 0.856 @900           | 31/80 (38.8%)     | 31/80 (38.8%)   | 0.477           |
| 5th   | 4-bit          | 16 / 8        | 3-tag                                    | checkpoint 900    | 0.848–0.856 @800–900 | 74/80 (92.5%)     | 72/80 (90.0%)   | 0.504           |
| 6th   | 4-bit          | 32 / 16       | 3-tag                                    | checkpoint 700    | 0.850 @500           | 47/80 (58.8%)     | 45/80 (56.3%)   | 0.517           |
| 7th   | 4-bit          | 32 / 16       | 4-tag (standardized reasoning, all rows) | checkpoint 800    | 0.852 @800           | **76/80 (95.0%)** | 74/80 (92.5%)   | 0.488           |

- **Well formed**: This scores whether the model output is in the required format. Depending on the trial, either of these two out format were required:
    - 4-tag (1st*, 2nd, 3rd, 4th, 7th): `<description>`, `<confidence-score>`, `<confidence-reasoning>`, `<review-triggers>`
    - 3-tag (5th, 6th): `<description>`, `<confidence-score>`, `<review-triggers>` — confidence-reasoning dropped for these two trials only, then reinstated for 7th.
- **Within 130 char**: This scores whether the model's alt text or description is at most 130 characters long. This number was decided from the recommendation of maximum alt text length that is usually around 125 characters.
- **Avg. similarity**:  This scores how the model's alt text or description is similar to the human reviewed and approved one in the validation dataset. This score is computer using "SequenceMatcher" from the python library "difflib". The same applies to 2nd trial.


Overall, the best adapter is 3rd-trial checkpoint 700. However, from this trial, the confidence-reasoning field was not standardized since it was written by humans with no clear guidelines, which make this field not reliable. The same applies to 2nd-trial checkpoint 700.
Thus, the next best adapter is 7th-trial checkpoint 800 which has the 4 tag output structure. Then there is 5th-trial checkpoint 900 which has the 3 tag output structure.



## Next Steps
Despite trying our best, we were limited by the amount of data and computing power we had. This project represents a great start into building an album cover alt text AI generator but as of now isn't ready for mass generation as its quality is not guaranteed.

The next steps will build on from our work and lessons learnt (see `full_fine_tuning_report.md` to learn about the entire process in details) and make a high quality consistent model. Next steps include:
- **Have a large training and validation dataset**: Our dataset was limited with a total of 524, 444 for training and 80 for validation. Thus, the different rial models reached their lowest valid loss around iterations 700 to 900, and from there they were basically memorizing the training data instead of learning from it. A larger dataset would mean more things that the model can learn from and become better in different types of covers. It is recommended to have at least 1,000 data in total with 80% training and 20% validation.
- **Tweak the different training parameters**: The main training parameters we changed past 1st-trial was lora-rank switching between 16 and 32 while keeping the **rank/α** ratio at the same to 0.5. With a larger dataset, playing with the different parameters, and just doing trial and errors, a great model can be made.
- **Have larger computing power**: Training a VLM takes a lot of computing power. We were using a macmini with only 24gb of ram and so were limited in what we could do. Namely, using an 8bit model crashed in 2nd-trial, and batch-size higher than 1 crashed constantly. Thus, having larger computing power could open more possibilities.
